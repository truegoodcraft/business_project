# BUS Core Data Lifecycle

This document summarizes where BUS Core data lives and how to interpret retention. `03_DATA_CONFIG_AND_STATE_MODEL.md` is the detailed authority map, and `OPERATIONS.md` is the diagnostic procedure.

## Canonical Windows storage

| Path | Purpose | Lifecycle notes |
| --- | --- | --- |
| `%LOCALAPPDATA%\BUSCore\config.json` | Launcher/UI/update/telemetry/write/policy config and top-level first-update-attempt flag | Canonical config; settings writes replace selected values through the config manager |
| `%LOCALAPPDATA%\BUSCore\app\app.db` | Production SQLite business state | Created/updated by canonical startup and business services |
| `%LOCALAPPDATA%\BUSCore\app\app_demo.db` | Demo SQLite state | Separate from production state |
| `%LOCALAPPDATA%\BUSCore\app\data\journals\*.jsonl` | Domain journals and restore/import audit | Append-oriented operational evidence; operator-retained |
| `%LOCALAPPDATA%\BUSCore\app\logs\core_<run_id>.log` | Per-run application/request log | New file per runtime run; operator-retained |
| `%LOCALAPPDATA%\BUSCore\app\data\session_token.txt` | Legacy/unclaimed bootstrap token mirror | Regenerated by runtime; secret material, never print or commit |
| `%LOCALAPPDATA%\BUSCore\state\telemetry_state.json` | Cumulative delivery counters, milestones, latest status/error/time | Retained when telemetry is disabled |
| `%LOCALAPPDATA%\BUSCore\state\telemetry_queue.json` | Current pending strict-schema events | Bounded to 100; best-effort cleared on opt-out |
| `%LOCALAPPDATA%\BUSCore\state\telemetry_dead_letter.json` | Newest rejected, overflowed, or exhausted records | Retains newest 100; best-effort cleared on opt-out; length differs from cumulative count |
| `%LOCALAPPDATA%\BUSCore\state\system_manifest.json` | Signed capability manifest | Generated Core state |
| `%LOCALAPPDATA%\BUSCore\state\capabilities_hmac.key` | Capability-manifest signing key | Secret local material |
| `%LOCALAPPDATA%\BUSCore\exports\*.db.gcm` | Encrypted database exports/staged uploads | Operator-managed retention |
| `%LOCALAPPDATA%\BUSCore\secrets\*` | Encrypted secret fallback and key material | Managed through approved application paths; never dump in diagnostics |
| `%LOCALAPPDATA%\BUSCore\updates\` | Manifest/download/version cache and `state.json` | Guarded manual staging and next-start handoff evidence |

`%LOCALAPPDATA%\BUSCore\app\config.json` is legacy compatibility input only. `data/index_state.json` and `data/settings_plugins.json` remain repo-local mutable-state drift rather than preferred durable authority.

## Lifecycle principles

1. Business truth is local SQLite and Core-owned journals, not telemetry.
2. Protected HTTP reads can still write request logs and claimed-session activity.
3. `GET /app/update/check` is specifically not a passive read: a performed check makes an outbound request, writes request evidence, and may enqueue product telemetry; while the first-check flag remains false, every performed check also retries the best-effort config write.
4. Product telemetry uses a strict non-business schema and exact acknowledgement. Update-route counts are a separate receiver aggregate.
5. Telemetry writes are atomic per JSON file but not transactional across state, queue, and dead-letter files.
6. Current runtime treats malformed/unreadable telemetry and update-state JSON as empty/default rather than quarantining it. Validate raw files before launch or interpretation.
7. Starting BUS Core can initialize/migrate/index, write logs, queue startup milestones, and begin delivery. It is not a read-only diagnostic.

## Telemetry retention and clearing

- `telemetry_state.json` counters are cumulative and acknowledged milestone keys remain across opt-out.
- `telemetry_queue.json` represents current pending records, including future-backoff records.
- `telemetry_dead_letter.json` retains only the newest 100 records, while `dead_letter_count` is cumulative.
- There is no time-based expiry for telemetry state, pending records, or retained dead letters. At low volume they can persist indefinitely until acknowledgement, rejection, retry exhaustion, count overflow, opt-out clearing, or separately approved maintenance.
- Disabling telemetry blocks new emits/new flush starts and attempts best-effort replacement of queue and retained-dead-letter contents with empty arrays, but does not cancel a sender request already in flight. Cleanup errors are non-fatal, so the preference/config response is not clearing proof.
- There is no dead-letter replay or malformed-file quarantine.
- An empty queue is not acknowledgement proof; records may have been acknowledged, rejected, exhausted, overflowed, cleared, lost to unreadable state, or never emitted.

## Operator controls

- Use application settings for ordinary config and consent changes. These are mutations and must not be performed merely for diagnosis.
- Use encrypted export/import workflows for database portability. Restore/import is a high-impact operation with maintenance, database, journal, and telemetry effects.
- Direct deletion or rotation of AppData state is destructive maintenance and requires an exact target, backup/retention decision, and explicit owner approval.
- `/transparency.report` summarizes policy/path/plugin information but currently hardcodes telemetry off. Use approved raw local state or protected `/app/telemetry/status` for telemetry delivery state.

For diagnosis, follow `OPERATIONS.md`; do not infer side effects from HTTP method names.
